## 异常发现

### 1. 权威规划状态漂移 — 置信度：高

**证据：** 根 `.planning/STATE.md` 记录 Phase 03 被沙箱阻塞、进度 33%；Phase 03 独立分支记录 100% 技术完成和 Gate G5 已捕获。根状态提交 `845ec2a83` 的时间晚于早期阻塞，但完成提交仍只留在另一条分支。

**影响：** “下一轮判断”会把已经完成的 Phase 03 再次推荐为待执行工作，造成重复开发和错误优先级。

### 2. 已完成修复未进入当前根分支 — 置信度：高

**证据：** 开发审计 10 个提交均包含于 `codex/balance-analysis-date-closure`，均不包含于 `codex/V1`。两者共同基点为 `845ec2a83`；此后 `codex/V1` 增加了性能提交和大量未提交的 market/risk home 改动。

**影响：** 不能把“测试通过、分支完成”等同于“系统主线已修复”；直接合并又可能覆盖或冲突当前根工作。

### 3. Phase 03/04 完成证据与标准产物不一致 — 置信度：高

**证据：** Roadmap 宣称 Phase 03、04 完成，但没有 Phase 03 SUMMARY/VERIFICATION，也没有 Phase 04 目录；Requirements 仍全部 Pending。

**影响：** 审计者无法从标准入口判断“实现完成”“业务选择采用”“正式进入主线”三者的区别。

### 4. 开发计划与实际执行存在替代关系 — 置信度：中

**证据：** 原开发计划 Task 5 计划补齐后端 Balance 日期 provenance，但提交 `c2e5f1709` 实际修复的是前端无可用日期 fail-closed；Task 6 的 Yield curve 已由 `982154c4b` 完成，但 PnL bridge 后端仍未传递 requested/resolved/as-of/fallback date，fallback 严重度也未合并进最终 quality flag。旧 `1c64430b9` 仅改前端状态展示，不能替代该后端合同。

**影响：** 当前开发计划不是可靠的完成清单；需要按实际代码重新标注“已完成、被替代、仍待处理”。

### 5. 工作区数量和残留过多 — 置信度：高

**证据：** 仓库注册 72 个工作区；Phase 02 工作区留有未跟踪的安全报告，Phase 03 工作区留有 `fake-governance/`。

**影响：** 容易再次从错误分支读取状态、误删仍有价值的成果，或把临时测试数据当成待提交内容。

### 6. 近期重复修改信号 — 置信度：低

**证据：** Stock Analysis 的页面、抽屉和测试文件在三次连续性能提交中反复修改。

**解释：** 有连续优化痕迹，但没有 revert、未解决冲突或当前 GSD 卡死的直接证据，因此不判定为失败循环。

## 已排除的异常

- **没有代码丢失：** Phase 03 实现和开发审计修复均有可解析提交和现存分支。
- **没有可直接 prune 的 Git 工作区：** 72 个工作区都仍在注册表中，不应批量删除。
- **没有证据表明当前开发审计分支中断：** `codex/balance-analysis-date-closure` 工作区干净，提交链完整。
- **没有证据支持继续 Phase 03：** 在月更且不常态追溯的业务约束下，它是低频保护机制，不是当前优先开发项。

## 根因判断

最可能的根因是：Phase 03、根规划更新、开发问题修复和后续性能工作分别在不同工作区推进，但项目没有强制指定唯一集成分支和单一规划状态写入点。完成证据因此停留在侧分支，根规划又在较晚时间提交了旧阻塞状态，最终让自动“下一步”流程读到了错误事实。

- `codex/balance-analysis-date-closure`：当前开发审计的最完整、干净集成线。先保留，不立即合并；待根 market/risk home 改动被提交或移出后，再吸收 `codex/V1` 的最新性能提交并运行冲突与回归检查。

### 应保留观察，不进入当前主线

- `codex/phase-03-incremental-rebuild`：保存技术证据，但按月更业务规则不直接集成。将其定义为“历史追溯能力候选/参考实现”，不是下一轮待办。

### 不应直接合并

- `codex/pnl-bridge-state-closure`：基线较旧且仅含前端展示；如果继续 PnL bridge，应在当前开发审计集成线上做小型后端合同修复，而不是合并该旧分支。

### 待确认后清理

- Phase 02/03 工作区中的未跟踪残留和大量长期工作区。应先生成“分支最后提交、是否被其他分支包含、是否有未提交内容”的清单，再逐个处理，禁止批量删除。

## 推荐动作

1. 把 `codex/balance-analysis-date-closure` 定为本轮开发审计的候选集成线，暂不删除。
2. 等根工作区的 market/risk home 改动完成或移出后，将根最新提交与该候选线做一次受控汇合和完整回归。
3. 用一个仅文档提交修正规划状态：分别记录“侧分支技术完成”“是否被当前业务采用”“是否已进入主线”，不要只写单一 Complete。
4. 将 Phase 03 标为低频历史追溯候选，不继续开发、不直接合并。
5. 真正的下一项代码工作若继续，应优先做小范围 PnL bridge 日期/fallback 元数据闭环；它与每月更新频率不冲突，因为解决的是页面回退证据，不是增加刷新频率。
6. 最后再做工作区清理；在此之前不删除任何现存分支或目录。
