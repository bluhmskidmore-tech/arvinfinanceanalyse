# 本轮系统优化交付方案

本轮先交付可独立验收的页面与接口改动，再收口类型门禁。当前 `codex/V1` 工作区有 931 项未提交变动；[实施与验收记录](system-cost-effective-optimizations-2026-09-22.md)中的 25 个候选文件指纹均保持一致，但不能把整份文件直接视为本轮新增代码。原有共享请求接入、产品损益读取模型、数据中心后端和另一任务维护的类型门禁交织在其中。直接提交整个工作区会夹带无关修改。

## 先确认交付基线

先核对现行系统的实际 URL、构建版本及其 Git 来源，再确定合并目标。当前本地 `codex/V1` 的 HEAD 为 `a97f0f3a`，本地与远端分支存在不同步状态；不能仅凭当前分支名假定发布目标。记录目标提交、候选文件哈希、现有依赖的负责人或上游提交，并保留当前 931 项工作区内容，不做整体 stash、reset 或清理。

以已确认的目标提交建立独立工作树和 `codex/` 分支。按作者改动前后的回执、局部差异和当前源码调用处移入本轮改动；共享文件逐段核对，不能把整个文件复制过去。先纳入本轮 25 个候选文件及实施记录，再逐项证明其依赖完整。数据中心至少要核对 `PlatformConfigPage.tsx`、`DataUpdateCenter.module.css`、`dataUpdatesClient.test.ts`，以及数据更新的 route、service、task；余额共享 transport 与产品损益已有响应模型也要检查上游归属。缺少依赖时，先把相应上游改动做成独立、可审查的提交或等待其合入，不用临时桩替代。

## 按功能交付

先在隔离工作树验证依赖，再按测试选择、余额变动读取、数据中心失败阶段、产品损益响应契约四个范围组织小提交或小 PR。每个范围只携带对应行为、测试和必要文档。依赖未合入的范围保留在后续 PR，不阻塞彼此独立的范围。合并前检查补丁与基线差异、文件归属和 `git diff --check`；不使用 `git add .` 从原混合工作区打包。

定向验收沿用已经跑通的证据：测试选择映射 102 项及关联业务回归 130 项；余额变动四文件 86 项；数据中心两文件 23 项；产品损益四文件 117 项，Python 测试显式提前加载 `_pytest_duckdb_guard`。集成时再跑前端 `typecheck`、`lint`、债务检查和本轮 10 项合成数据浏览器场景。通过标准是隔离工作树中的结果，不把 9 月 22 日混合工作区的通过记录当作新提交的 CI 结果。

## 类型门禁单独收口

先在同一目标提交的干净工作树加入 checker 和可信历史基线，使用固定的 Python 3.11、mypy 1.20.1 与锁定依赖运行门禁，记录目标提交本身的未豁免诊断；随后加入待交付改动并再次运行，区分基线分支原有问题与本轮引入问题。9 月 22 日混合工作区的 667 条是新增或身份变化诊断快照，不能直接当作本轮需修复的清单；现有日志每文件最多打印 10 条，522 条示例也不是完整逐文件分布。诊断归属须从同一源码快照的完整结果生成。

类型门禁的 checker、基线及 CI 改动单独审查。四文件自测 84 项通过只证明门禁规则有效；真实门禁未豁免身份降为零，才说明该目标分支可以启用严格 CI。对已经消失的历史身份，可经复核后收紧基线；不能把新增诊断写入豁免来换取通过。若目标分支本身仍被类型债务阻断，先交付通过现有 CI 的独立功能 PR，类型门禁 PR 保留为待处理项并给出具体文件归属，不宣称五项均已上线。

## 合并与运行验收

每个 PR 通过实际远端 CI 后再合并。按现有发布流程部署对应前后端版本，并在实际 URL 核对构建身份、页面路由和相关只读接口。数据中心发布失败和余额读取失败使用受控合成场景验证提示及重试，不人为制造生产写入失败。最终回执分别记录已合并的 PR、构建版本、页面结果、未通过的类型门禁和未部署的范围；代码合并、页面可见与业务对账分别报告。
