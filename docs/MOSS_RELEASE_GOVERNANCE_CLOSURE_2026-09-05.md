# 发布治理依赖收口

本轮将此前未提交的发布治理实现整理为可以独立校验的依赖组，并修复审批与重复请求处理中的失败放行问题。范围包括审批契约、发布状态机、仓储、命令行入口、注册表及对应数据库迁移，不代表业务页面已获得正式发布批准。

原实现把部分非布尔可信标记当作真值使用，持久化回执缺失、请求摘要错绑或审计事件不完整时也可能返回成功。修复后，审批必须提供明确的 `true` 可信结论；重复请求仍要检查当前审批的撤销和有效期。稳定请求身份不再包含每次重验都会变化的检查时间，合法重试不会因此冲突。

激活结果与冻结清单、完整作用域、修订号、审批证据及已提交的独立历史事件绑定。持久化回执和事件发生分歧时拒绝返回成功；历史发布请求的重放使用历史事件证明结果，不要求可变的当前 alias 仍停留在原版本。这保留了后续发布完成后重试旧请求的合法行为，也避免并发发布导致已完成操作被错误判断为失败。已知仓储错误继续映射为明确的业务错误，未知错误向上传递，不伪造成功回执。

## 依赖范围

本轮依赖组包含 15 个生产、配置及迁移文件。`backend/alembic/env.py` 和 `backend/app/models/__init__.py` 只纳入 release 表的注册片段；工作区中的其他模型注册保留在原处。子迁移 `c2e94f6a8b10` 的父迁移 `7d1a2c3e4f50` 尚未存在于原 HEAD，因此一并纳入该父迁移及匹配的 AgentAudit、AgentPrompt 两个表模型。它们只闭合迁移链及元数据，不启用 Agent 功能。

注册表依赖的 owner decision 检查脚本也纳入提交。注册表现有 16 项仍为 `PENDING`，结构通过不等于可发布：实际发布资格仍会被阻断。没有为缩小依赖组改写既有迁移父版本，也没有把其他未提交业务功能混入本轮。

## 验证与操作边界

验收从已提交 HEAD 归档组装候选，只覆盖明确的依赖文件，再运行审批、状态机、仓储、命令行、异常边界和独立损坏回执回归。测试使用临时 SQLite 和内存证据。Alembic 的升级、降级及元数据核对也只针对候选临时 SQLite，验证三张发布表与两张父迁移表可以闭合。

最终测试数量、文件哈希、独立复审及提交回执保存在 `.codex-tmp/release-closure-2026-09-05/`。Ruff 使用既有固定版本和异常基线，本轮不提高债务上限。真实 PostgreSQL 并发发布测试未执行，不能将 SQLite 结果视为 PostgreSQL 并发验收；对应测试需要独立、可销毁的测试数据库。

本轮没有向真实数据库应用迁移，没有执行实际发布或回滚，也没有重启正在运行的服务。后续部署应按环境变更流程应用迁移，并在受控 PostgreSQL 测试库完成并发验证。其余未提交改动和原有暂存内容继续保留，不能据此宣称整个工作区的技术债务已经清零。
