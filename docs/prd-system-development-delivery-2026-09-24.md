# MOSS 开发交付流程改进 PRD

版本：1.0。编写日期：2026-09-24。状态：可交给执行模型实施，本文本身不代表改造已完成。

## 1. 要交付什么

本项目的目标是让开发者能够从一个明确版本开始，用已有工具完成一项业务修改，验证相关行为，并把结果交付到指定的日常开发入口。首期交付范围为：**开发基线对齐、数据更新到余额分析的完整验收、对应变更的 CI 接线和交付回执**。

用户目前感受到的瓶颈是开发成果不断增加，但仍难以确认日常版本包含哪些修复、一次修改需要验证什么，以及测试通过后是否真正改善了使用入口。此前完成的局部修复保留价值，但不能代替本 PRD 的整体交付。

执行模型应把工作拆成下文的有界任务。每次只推进一个任务，通过相应验收后可继续下一项；无需对已授权的本地读取、隔离修改和定向测试反复请求确认。遇到真实的版本选择、业务口径或运行权限缺口，应提出具体问题，并继续不依赖该答案的工作。

## 3. 用户场景与成功标准

开发者接手一个任务时，能找到当前集成分支、运行入口、依赖版本、涉及的业务模块和最小验证命令，不需要先阅读全部历史报告。

开发者修改每日余额更新或余额分析时，能够在隔离环境中用明确的合成输入验证请求、执行、结果和页面状态。测试失败能指出所在环节，不会由旧归档、跳过测试或模拟成功掩盖。

开发者提交修改时，实际使用的 PR 目标分支能够选中并运行相关检查。已验证成果进入集成分支后，还要核对指定日常入口的构建与相关行为，才能报告“已生效”。

| 验收对象 | 首期完成标准 |
| --- | --- |
| 开发基线 | 选定基线有依据；干净检出可复现启动和定向检查 |
| 改动归属 | 每份纳入的修复有独立差异、来源和验收记录 |
| 业务流程 | 指定报告日的更新请求、结果日期和余额页面一致 |
| 异常流程 | 缺文件、失败、重复提交、落后状态有明确可见结果 |
| 开发反馈 | 相关快速检查目标为暖环境 300 秒内 |
| CI 覆盖 | 有实际事件记录证明检查执行，未选中不能当作通过 |
| 交付状态 | 区分隔离验证、集成、运行生效和业务对账 |

300 秒是待测的开发反馈目标，不是现有能力或硬性承诺。不得为达标删断言、缩减必要覆盖、放宽守卫或抬高债务基线。依赖安装、冷启动和托管 CI 时间单独记录。

## 4. 范围与实施边界

首期主流程为 `/platform-config` 中明确报告日的 `balance_daily` 请求，经过现有数据更新服务和后台任务，再核对 `/balance-analysis` 的日期、结果和质量状态。`balance_daily` 的既有必要步骤仍按现有定义执行，不能为了缩短测试把必要步骤从业务工作流删除。

`/balance-analysis` 与 `/balance-movement-analysis` 是不同页面；`balanceAnalysisClient.ts` 与 `balanceMovementClient.ts` 也不是同一客户端。此前余额变动日期守卫可以作为已验证修复纳入，但不构成首期主流程已经贯通的证据。

本轮不扩展到完整损益历史重算、所有页面迁移、全仓类型债务清零或通用平台重建。数据库结构、认证与权限、队列和调度基础、缓存基础、全局状态架构仍受根目录规则保护。只有本流程的直接根因证据才能支持最小必要调整；跨越这些边界时先记录证据和影响，不能借此重写整层。

执行本 PRD 默认可做本地只读调查、独立工作树、合成数据测试、代码修复、局部构建和本地提交。本文不构成推送内部材料、部署到日常入口、运行真实财务写入或历史补算的新增授权。已有明确会话授权继续有效；若下一步确需新增授权，先完成可审查的提交、执行方案及回退方案，再只询问缺失的那一项。

## 5. 执行前必须遵守的规则

先读 [代码导航](agent_codebase_map.md) 和根目录 [AGENTS.md](../AGENTS.md)。前端、后端及测试改动分别读取最近的路径规则；正式指标或页面契约变动使用相应 MOSS 技能。文档、源码、测试和实际运行不一致时，记录差异并沿当前调用链取证，不从历史报告推断现状。

共享工作区已有大量他人改动。不得执行全量 `git add`、`reset --hard`、`git clean`、整树 stash、覆盖复制或自动 rebase 来获得“干净状态”。先记录路径清单及本任务相关文件指纹，再在独立工作树实施。不要读取全部 1,023 个文件的内容；全局只做 Git 元数据盘点，内容调查限于当前任务闭包。

所有源码使用无 BOM 的 UTF-8。含中文文件用 Node `fs` 或专用编辑工具读写；不用 PowerShell 文本重定向、`Get-Content` 或 `Set-Content`。既有暂存内容保持原样，只提交本任务明确列出的路径。

金融计算继续由后端正式计算模块承担。不得在前端补算正式指标、以零代替缺失、使用邻日数据掩盖目标日缺口，或伪造身份绕过权限。测试使用隔离目录与合成数据，保留已有 DuckDB 和生产数据访问守卫。跨工作树使用解释器时，必须核对实际导入文件来自受测工作树，不能无声导入共享目录的 editable 包。

代码符号修改前按根规则做 GitNexus 影响分析。优先复用与受测源码匹配的索引，不为每项微小编辑重复全仓重建；HIGH/CRITICAL 在编辑前报告。索引缺失、过期或覆盖不足时按根规则处理，失败后记录工具限制并补当前定义、直接调用与相关测试。不得把零调用或低风险当作完整覆盖，也不因工具故障启动额外的平台修复。本 PRD 不自行修改 `AGENTS.md` 的工具要求。

## 6. 任务一：确定开发基线与运行入口

本任务只调查并形成执行依据，不修改业务源码。

入口为 Git 元数据、已有启动文档、[验收要求](acceptance_tests.md)、[测试说明](TESTING.md) 和现有 `scripts/dev_runtime_control.py`。先检查该脚本的帮助与实现，仅使用其只读状态、计划或探针能力；不得把状态检查扩展为启动、重启或构建切换。

需要完成的动作：

1. 记录本地 HEAD、跟踪引用、分叉关系、工作区状态和现有工作树。需要比较远端现状时执行只读查询，不能先 pull 合并。
2. 从现有配置和启动进程定位用户实际入口、前端构建标识、后端源码位置及可获得的规则版本。没有来源证据的字段写 `PENDING`，不能由端口或健康检查猜测版本。
3. 比较与首期相关的候选基线，说明关键功能在各版本中存在、缺失或已有更强实现。按行为比较，不能只比较文件是否同名。
4. 选择可追溯的集成起点，记录选择原因。远端引用不能自动代替运行证据；若两份不可兼容版本都被实际使用，提出一个具体的基线选择问题。
5. 在独立工作树核实启动和定向验证所需依赖、版本、配置及测试资产。优先复用已有安装流程，不复制真实业务数据或整个虚拟环境。

输出为 `docs/system-development-delivery-status.md` 的“基线与入口”部分。记录候选、选定基线、实际入口、未决事项、解释器及 Node 版本、相关文件指纹和可复现命令。该状态文件是后续模型接手入口，不另造管理系统。

验收：能够解释“从哪个版本开始、为何选它、日常入口对应什么版本、还有什么未确认”。如果运行版本无法识别，隔离实现仍可推进，但运行生效验收保持待办。

## 8. 任务三：建立同一报告日的业务验收样例

先读 [数据更新中心](data_update_center.md) 和 [页面契约](page_contracts.md) 中 `/balance-analysis` 的对应段落。核实选定基线中的入口是否与下表一致，发现差异先更新调用记录。

| 层次 | 首查文件或入口 |
| --- | --- |
| 数据中心页面 | `frontend/src/features/platform-config/DataUpdateCenter.tsx` |
| 更新客户端 | `frontend/src/api/dataUpdatesClient.ts` |
| 请求接口 | `backend/app/api/routes/data_updates.py` |
| 请求服务 | `backend/app/services/data_update_service.py` |
| 后台执行 | `backend/app/tasks/data_update_center.py` |
| 余额接口 | `backend/app/api/routes/balance_analysis.py` |
| 余额服务与物化 | `balance_analysis_service.py`、`balance_analysis_materialize.py` |
| 余额前端 | `balanceAnalysisClient.ts`、`balanceAnalysisOverviewClient.ts` |
| 余额状态与页面 | `useBalanceAnalysisData.ts`、`BalanceAnalysisPage.tsx` |

明确日期 `D`、`balance_daily` 范围和合成输入版本。复用现有 fixture、仓储和物化测试入口，构造足以核对报告日、记录数及一项有独立预期的正式余额结果的小样本。预期来自手工推导或已有独立参考，不导入被测计算函数来生成自己的正确答案。

允许替换外部供应商、真实文件投放和等待调度等环境边界；不得把所有计算、持久化及发布阶段都 mock 成成功。必须标清哪些环节真实执行、哪些被替代。隔离端到端测试通过只证明该合成范围，不代表真实财务对账通过。

至少覆盖下列场景，优先补在现有所属测试模块：

| 场景 | 必须观察的结果 |
| --- | --- |
| 指定日期正常完成 | 请求日期、结果日期和页面所选日期一致 |
| 日期所需文件缺失 | 有明确原因，不展示为已更新 |
| 同一活跃请求重复提交 | 按现有规则复用原请求，不产生重复执行 |
| 目标日结果尚未可用 | 保留落后或缺失状态，不暗中切到其他日期 |
| 计算完成但发布失败 | 保留完成与失败回执，不把整体显示为成功 |
| 页面读取失败或 DTO 非法 | 显示可理解的失败状态，不填零掩盖 |
| 合法零余额或空结果 | 与缺失、异常状态区分 |

发布失败场景只使用选定流程中实际存在的阶段；不存在该阶段时记录 `不适用` 和源码依据，不能为满足表格新增发布框架。请求复用也只验收已有日期、范围及幂等规则，不在首期扩展新规则。

验收：同一合成样例具有请求回执、后台结果、接口响应和页面断言；任何日期不一致、假成功或错误零值都有可失败的断言。先保存当前结果，发现缺陷后由下一任务修复。

## 9. 任务四：修复样例暴露的实际断点

仅修复上一任务有反例证明的断点。每次变更先写清触发条件、错误结果、正确结果、所属层和直接调用者；复用现有 helper、契约与错误处理模式。

允许范围是上表调用链中的最小必要文件及所属测试。新增共享抽象、配置项或依赖必须说明现有入口无法满足哪条已验证要求。日期和金额口径不明确时停止该改动，不能用模型判断补业务定义。

对修复分别保存改前失败与改后通过，汇合后复跑相关连接处。至少检查日期从提交到读取的传播、失败回执到页面状态的传播，以及重复请求是否仍复用。原有与本次无关的失败单独登记，不通过关守卫或修改预期使它消失。

验收：任务三适用场景在当前集成分支全部有结果，新增失败已修复，未解决项有具体责任边界。模块各自通过不能代替调用连接处验收。

## 10. 任务五：把相关验证接入实际开发与 CI

先核实目标集成分支、当前 `.github/workflows/ci.yml` 和 `scripts/check_caliber_gate.py` 的实际选择结果。复用既有后端执行清单、差异映射和前端 npm 命令，不先创建新的通用测试编排器。

验证分为三个用途：开发中的定向反馈、合入前的必要门禁、既有全量与定时检查。用途不同必须在报告中区分，快速检查不能替代正式计算变更所需的 canonical gate。

首期只补首期路径的选择遗漏。用一条受影响源码路径和一条无关路径核对选择器；再在独立测试样例中引入明确失败，证明失败会传到命令和 CI 状态。不得在共享工作区临时破坏业务代码。

如果目标 PR 分支不是 `main`，必须处理该目标下检查不执行的问题。先计算当前 workflow 各 job 的事件范围，优先利用已有条件；若只能通过一个窄工作流解决，复用现有命令并说明理由。不能直接扩大全局 PR 触发范围而不评估所有作业的负载，也不能仅新增一个不会被触发的测试文件。

类型和异常捕获检查维持问题身份与工具版本约束，首期不得抬基线、开启忽略失败或扩大豁免。全仓门禁若因既有债务失败，记录具体身份和基线证据；可以报告当前切片未新增问题，但仍须把整体门禁记为失败或待处理，不能宣称可合入。只在同环境的基底对照后才能称为原有问题。

Agent Eval 的自身修改可能按完整性规则得到 `void`。这可以用于检查编排和归档，不能证明可信业务探针跑过，也不能用来计算探针提速。只有未修改评测基础设施且真正适用的变更，才可测可信回放耗时。

验收分两层：本地选择与失败传播测试通过；托管 CI 有实际事件、目标分支、执行命令和结果。没有推送或运行权限时先完成本地配置与证据，把后者记为待验证，不捏造 CI 运行编号。

## 11. 任务六：交付、日常入口核验与接手

保存干净的集成提交、所选基底、必要配置、依赖版本及最短启动说明。对照任务一列出已纳入、等价已有和仍待处理的修复，保留原工作区全部既有改动。

在已有授权范围内使用既有运行控制流程交付。需要新增部署或业务写入授权时，先提供确切提交、目标入口、要执行的命令、影响及回退方式；不提前切换日常服务，不假装已部署。回退以既有构建或提交选择机制为准，不恢复数据库副本来模拟代码回滚。

核对用户实际使用的 URL、前端构建身份、后端相关版本及任务三的可观察行为。生产构建通过、health 200、不同端口成功都不能单独证明日常入口已生效。若没有获准进行真实数据写入，可用既有合法只读接口核对现有日期；明确保留真实更新和业务对账的未验证范围。

在固定机器、依赖和缓存条件下记录开发检查耗时。首期快速检查最多取三次可比样本，记录中位数和范围；首次安装另计。若依然超过目标，按实测最慢步骤提出一个后续任务，不在交付末尾扩展为性能重构。

验收：另一个执行模型仅阅读 PRD 和状态文件，就能定位当前分支、剩余任务、验证入口和运行状态。只完成隔离测试时最终状态为“隔离验收通过”；完成集成但未交付时为“待日常入口验收”；不能提前写“系统瓶颈已解决”。

## 12. 已有验证入口与命令使用方式

下列文件和命令在编写时的共享工作区存在。候选基线可能不同；执行前先核对，不能遇到文件缺失就无声跳过，也不能为了凑命令把整个测试目录搬过去。

在已确认依赖和导入路径的工作树中，按涉及范围选用：

```text
python -m pytest tests/test_data_updates.py tests/test_global_data_refresh.py -q
python -m pytest tests/test_balance_analysis_api.py tests/test_balance_analysis_service.py -q
python -m pytest tests/test_balance_analysis_snapshot_fact_consistency.py -q
npm --prefix frontend run test -- dataUpdatesClient.test.ts DataUpdateCenter.test.tsx
npm --prefix frontend run test -- useBalanceAnalysisData.test.ts BalanceAnalysisDateSemanticsContract.test.tsx
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend run debt:audit
```

`python` 必须先解析为状态文件中记录的解释器。Windows 必要时用 `npm.cmd`。上述命令是可定位的起点，不是所有任务必跑清单，也不保证已覆盖任务三全部场景；缺口补在所属模块，并保留生产数据访问守卫。

改动映射使用 `python scripts/check_caliber_gate.py --base-ref <本次实际基底> --dry-run` 查看选择，再按变更风险真正执行。占位符必须替换为已核实引用。涉及正式计算或 release cutoff 时按现有规则执行 `python scripts/backend_release_suite.py`，不能用另一套自定清单替代。

相关门禁使用当前脚本实际支持的参数：`python scripts/check_mypy_baseline.py`、`python scripts/check_ruff_ble001_baseline.py`。本 PRD 不要求自动运行 `--update-baseline`。先核对选定基线的脚本、锁文件和工具版本；全量门禁只在需要归因或验收时运行，不在每次小编辑后重复。

浏览器验证复用现有 Playwright 配置、明确的本地端口和合成响应；所有 mock、显式参数、端口覆盖及选择范围写入证据。真实接口及正式数据验证另行记录，不混算测试数量。

## 13. 状态文件与每批回执

执行模型维护一个 `docs/system-development-delivery-status.md`，不为每次工具调用另建报告。详细日志放在独立证据目录，例如 `.codex-tmp/system-development-delivery-<日期>/`，只在状态文件中引用。证据不得包含密钥或未经授权外传的银行内部数据。

状态文件至少包含：

- 当前任务全名、执行状态、下一步动作。
- 选定基底、集成分支、当前提交、工作树路径与运行入口。
- 本批修改路径、根因、直接调用者和相关源码指纹。
- 实际命令、环境、退出码、通过/失败/跳过数量与日志位置。
- 改前反例、改后结果、独立预期及模拟边界。
- 必要门禁、CI、运行生效和业务对账各自的状态。
- 原有失败与新增失败的证据，以及未纳入的既有改动。
- 真正需要委托方回答的问题及其阻塞的具体动作。

任务状态只使用“未开始、执行中、受阻、隔离验收通过、已纳入集成分支、日常入口已生效”。补充“业务对账通过”必须有单独日期、来源和口径证据。文档完成、测试通过、已提交、已部署不能互相替代。

每次停止或交接前更新状态文件。下一模型从第一项未完成任务继续，先检查源码是否变化，不从头重复盘点或沿用过期的通过结果。指纹或输入变化时，只重做受影响的验证。

## 14. 首期之后的架构工作

首期完成后，再根据实际交付记录选出最多三个结构热点。候选依据应包括修改传播范围、反复返工位置、测试隔离困难或明确的运行耗时；文件长、命名不好看和抽象不够优雅不能单独成为重构理由。

每个热点另写一张小任务卡：具体触发场景、现有依赖、允许修改的边界、行为等价测试、预期减少的开发成本和回退方式。每次只实施一个热点。产品损益、数据更新发布、存量类型债务和前端耦合不能在一个提交里同时处理。

本节是后续排队规则，不是要求执行模型在首期末尾自动展开全仓重构。未来开发仍会产生债务，首期要建立的是识别、拦截和逐项偿还的工作方式。
