# MOSS 页面响应与数据刷新优化方案

日期：2026-09-10。状态：第二轮后端优化与两个比较期补算已在本机系统生效，实际洞察接口 P95 为 2.067 秒；前端候选尚未发布，整体体验目标尚未达标。本文件保留初始调研、总体方案与目标，最新事实和验收结果见 [第二轮验收记录](F:/MOSS-V3/docs/performance-improvement-round2-2026-09-10.md)。

建议从已经实测的业务损益洞察慢查询开始，逐页达到可重复验证的响应目标，再处理后台更新期间的资源竞争。复用现有预计算、请求回执、后台任务和前端查询状态。是否需要增加存储或部署组件，由后续分段耗时与容量测试决定。

**已知情况与待确认事项。** 本次对运行中的本机系统做过单次只读测量：首页主快照 8–18 毫秒，市场快照 29 毫秒，首页收益趋势 27 毫秒；2026 年截至 8 月 31 日的业务损益洞察返回成功，耗时 51.561 秒。慢查询执行期间，首页快照的一次读取耗时 689 毫秒。上述数字不是冷启动结果、P95 或并发容量结论；最后一项提示可能有资源竞争，尚未证明因果。浏览器已确认首页可以展示实际数据，但未取得可用的浏览器性能时间线。

代码表明正式损益更新已调用业务损益预计算，年度、月度读取也已优先尝试读取持久化结果。因此不能把根因写成“系统没有预计算”。当前待确认的是预计算命中率、来源校验成本、洞察诊断成本以及数据库等待时间。整个系统的慢接口分布、当前硬件容量和实际同时在线人数也待测量。

**验收目标。** 以下为拟定预算，尚未达成。先在当前硬件、固定数据版本和构建版前端上测单会话，再逐级测 5 个、10 个模拟活跃会话。请求节奏应模拟实际看板使用，不把无限并发请求数当作用户数。

| 场景 | 拟定目标 |
| --- | --- |
| 点击、切换标签后的可见反馈 | P95 不超过 100 毫秒 |
| 返回已有有效缓存的页面 | P95 不超过 300 毫秒 |
| 常用页面首次出现核心数据 | P95 不超过 1.5 秒 |
| 普通读取接口 | P95 不超过 500 毫秒 |
| 有效预计算已就绪的洞察接口 | P95 不超过 1 秒 |
| 后台重任务运行时的普通读取 | P95 不超过 1 秒 |
| 同一筛选条件下刷新 | 保留内容，无整页清空 |
| 切换报告日后旧请求返回 | 不覆盖新日期的数据 |

复杂计算本身单独计时，不承诺都能在一秒内完成。没有有效结果时，页面应及时给出真实的准备中、失败或来源缺失状态；加载提示出现不计作核心数据已显示。后台排队时间与实际计算时间分别报告，现有数据中心每五分钟检查请求的周期不能描述成即时执行。

**第一批：定位并修复业务损益洞察查询。** 范围为 `/pnl-by-business-insights` 及其年度、月度、对比期读取依赖。先复用 `perf_logging.py` 的计时习惯，记录本年累计、上年同期、滚动月度、对账诊断、结果封装各段时间；同时记录预计算是否命中及未命中原因、数据库查询次数、读取规模和锁等待。分别测已有有效预计算、预计算缺失、来源版本变化和应用进程重启后的读取。冷缓存场景在隔离环境复现，不清空运行系统的缓存或重启用户正在使用的服务来制造样本。

优先排查当前日期及洞察实际需要的对比日期是否已有有效预计算。已存在结果但读取仍慢时，继续拆分来源指纹校验和诊断计算；同一请求内相同期间的重复读取可以共享，但必须保证使用同一个可验证的数据版本。若耗时集中在数据库扫描，就在现有仓储查询内减少扫描范围和重复取数。若缺失结果触发重算，则复用现有按指定截止日重建入口，只补齐已确认的依赖日期。

如年度、月度结果都已快速返回，而洞察组合或对账诊断仍占主要耗时，再评估将该页面结果纳入现有预计算任务。现有表已有结果类型和版本字段，能否复用须核对仓储写入、替换范围、契约和治理证据后决定，不能预先认定兼容。正式数值计算继续使用后端正式计算代码。

本批完成条件是有效预计算场景达到一秒预算，并说明剩余冷计算耗时。优化前后的金额、FTP、日期、缺值、质量状态、组件证据和正式使用权限应保持一致。错误和缺失来源必须仍能触发既有保护。第一批先保持现有读取契约；如需让缺失结果改为异步准备，另行完成前后端状态契约和有权限的提交动作，不能让只读 GET 隐式获得写入权限。

**第二批：让切页和刷新保持连续。** 先改损益洞察页，再改首页，之后按测量结果推进产品分类损益、余额分析、市场与风险页面，每次只交付一个页面。复用现有 QueryClient、查询键、页面状态组件及路由懒加载。同一日期、同一筛选条件刷新时保留现有内容，局部显示正在更新；切换日期时，旧数据若保留，必须明确仍属旧日期，不能挂在新日期标题下形成经营结论。相关组件全部准备好后再切换同一组财务读数。

首页已有多层固定延迟和空闲加载。通过浏览器时间线确认每层实际收益，只移除没有数据依赖的串行等待，保留首屏、屏幕外图表和正式报告日之间的必要约束。表格明细采用现有分页或虚拟列表能力，只有实际渲染成本证明需要时才调整；摘要接口避免携带首屏未使用的大批明细。

查询取消是一个单独的共享接口改动。当前 `transport.ts` 使用自己的超时 AbortController，普通 `requestJson` 也未接入查询层信号。实施时先对相关符号做影响分析，再以兼容参数贯通页面查询、领域客户端和传输层；区分主动取消与超时错误，保留超时保护。切页取消仅针对已无消费者的请求，共享查询仍有订阅者时不得提前取消。浏览器取消不代表后台数据库计算已经停止，后台工作量仍由第三批约束。

本批通过条件包括首次进入、返回、同日刷新、快速连续切日期、慢响应、失败和空数据。旧请求不能覆盖新筛选，刷新失败时保留的数据必须带失败状态，滚动位置和键盘焦点应保持合理。仅修改加载顺序不得改变财务指标来源和数值。

**第三批：保障更新时仍能正常浏览。** 区分用户读取数据和数据中心重建数据。前者读取现有结果，后者沿用请求服务与后台任务的执行回执。已经存在的预计算任务状态、重建动作及同年度重复任务保护应优先复用。先核验实际运行的后台工作器是否可接收任务，避免页面提示已提交但没有执行者。

数据中心每一步补齐耗时与处理范围的可见证据，重点判断产品损益步骤处理历史月份是否为总耗时主因。若要缩小重算范围，先列清单日变更影响的月度、累计、同比和滚动窗口。历史文件替换可能影响后续累计期间，不能把“只算变更日”当作普遍正确的增量规则。只对已确认的依赖范围重算，并与现有完整结果做对照。失败后保留成功步骤与错误回执；当前没有逐步骤断点恢复，不能在本批之前宣称具备这一能力。

结果生效继续保留来源版本、规则版本、FTP及手工调整状态校验。后台任务和 API 可能位于不同进程，只清理工作器内存无法证明 API 已失效。先复用现有持久化版本与回执识别变更；如实测证明每次读取重新扫描来源指纹过重，再最小调整版本校验方式，并覆盖同日替换、历史更正及并发更新。TTL 到期不能作为财务结果有效性的唯一判断。

当前完整更新没有跨步骤事务回滚。展示端需区分“某一步完成”与“同一报告日所需模块全部可用”，使用既有就绪证据防止把部分写入当成完整新版本。若要增加独立的发布版本或可持续读取的上一版本，这属于需要明确设计和验证的存储改动，不能把它写成已有功能。

在隔离环境测量重任务下的 CPU、内存、磁盘、数据库等待和普通查询耗时。证实有竞争后，优先约束现有重任务并发、合并重复计算并减少无效重试。DuckDB 文件锁与多进程读写边界必须单独验证；调整线程数量或把计算移到另一个进程不等于已经解决锁问题。只有仍不能满足浏览预算且证据指向共享存储或资源上限时，再提出独立读取副本、快照发布或部署拆分。

**第四批：形成可重复的全系统验收。** 先测六类代表页面：首页、业务损益洞察、产品分类损益、余额分析、市场工作台、风险工作台。其余页面按主导航清单记录首次进入、返回和刷新表现，以最慢且使用频繁的页面决定后续顺序，避免只优化首页。

固定前后端构建标识、机器、数据版本、报告日、缓存状态和负载模型。每个稳定场景至少采集 30 个样本，报告样本数、P50、P95、最大值、失败数以及缓存命中情况；这个样本量用于初轮筛查，不冒充大规模容量认证。冷启动另做多次独立重放。分级并发从单会话开始，只有上一档稳定才继续，出现持续排队或资源饱和就停止升压。更新、历史替换和故障注入在隔离数据副本上完成，不对运行中的财务库做压力写入。

浏览器验收至少包含十分钟连续导航和刷新，检查主线程长任务、请求瀑布、重复请求、内存持续增长及后台页面轮询。通过窄范围验证后再扩大；同一个数据版本下结果不一致、失效不生效或正式使用状态改变，均判定不通过，即使速度达标。

前端先运行相关页面及传输层的定向 Vitest，再按前端约定执行 `npm run lint`、`npm run typecheck`、`npm run debt:audit`。首页性能采样优先检查并复用 `frontend/package.json` 中的 `guard:home-startup:live` 和 `profile:home-snapshot:live`，浏览器交互沿用现有 Playwright 页面测试。修改数据更新编排时增加 `tests/test_data_updates.py`、`tests/test_global_data_refresh.py` 的定向验证。上述为方案阶段的检查安排；实际执行结果以本轮验收记录为准。

每批独立提交和发布，记录改动前后版本与同条件结果，保留可回退的应用版本。金融数值、权限或来源校验出现回归时，回退对应批次，不用放宽校验、增加超时或更换旧数据掩盖问题。没有测量证据时不排整个平台重构，也不承诺整项工作的固定工期；第一批分段结果出来后再估后续工作量。

首轮应交付业务损益洞察的分段耗时、最小修复、数值与来源一致性证据，以及同条件复测结果。随后再推进页面体验和更新期间的响应保障。
