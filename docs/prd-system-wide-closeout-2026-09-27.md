## 收口范围与范围冻结

首页、固收与风险、余额与经营损益、宏观与行情、股票、Agent、数据更新等作为查漏方向，最终条目以实际导航、路由和已约定功能为准。每个实际入口都必须有结论，不能因为修复困难而静默移出范围。原本明确排除、预览或尚未启用的功能保持原边界，并说明用户能够看到的状态；页面存在不代表正式金融口径已经晋升。

清单建立后冻结本次功能范围。新增功能、非必要美化、通用架构重建、与本次交付无关的性能优化进入后续事项。新发现只有在能够说明具体触发条件、错误结果及受影响入口时，才可判定为本轮阻断。

正确性错误、关键流程失败、必需门禁失败、版本混用导致结果不可信属于阻断候选。一般命名、文件长度、视觉偏好和可记录的非阻断债务不自动扩大本轮。具体严重性沿用 [现有发布标准](V3_CUTOFF_EXIT_CRITERIA.md)，必需门禁不能由模型自行豁免。

## 已有用户验收如何复用

优先从现有对话、截图、验收记录和运行回执中找出用户已经确认的具体业务行为。确认“某页能正确完成某件事”后，保留这项业务结论；不能要求用户重新证明自己的判断，也不能把“很多已验证”扩大成全系统全部通过。

对每项结论，只核对其后是否发生相关变化，包括页面和 API、正式计算规则、共享读取或缓存、数据来源及报告日语义。没有相关变化，复用原结论；存在变化，补验受影响的行为与直接连接处。版本信息不全时，记录“用户已验收，版本对应待核对”，由执行模型先查构建、相关差异和既有记录，不能直接降级为未验收。

确实找不到具体页面或确认范围时标记 `PENDING`，先汇总成一个简短问题，并继续不依赖答案的工作。不得逐页要求用户再走一遍，也不得因一个条目缺证据而重跑所有功能。

状态清单每行代表一个可描述的用户行为，字段保持精简：

| 字段 | 内容 |
| --- | --- |
| 入口与行为 | 实际路由、用户要完成的事 |
| 用户验收 | 已确认、待对应或未确认 |
| 版本与日期 | 相关源码指纹、构建、规则及适用报告日 |
| 后续影响 | 无相关变化、存在变化或待核对 |
| 本轮结论 | 复用通过、补验通过、阻断或待补证据 |
| 证据与负责人 | 原始回执、日志或测试位置及唯一负责人 |

这些字段写入现有进度文件的附表或其单一链接，不另建第二套状态台账。详细命令日志继续放在现有证据目录。

## 6sol 与 luna 的分工

本文中的 6sol 指 `gpt-6-sol`，luna 默认指 `gpt-6-luna`。模型名称用于后续任务安排，不要求中断正在运行的负责人或切换已有任务模型。若执行环境不可用，应如实记录并由现有主代理接续，不能假称指定模型已执行。

6sol 负责范围清单、已有验收映射、任务归属、阻断判定、跨模块连接复核和最终结论。涉及正式金融含义、共享边界、版本选择或多个模块冲突的事项，由 6sol 汇总证据并按仓库规则处理；口径不明确时保留待裁定，不交给模型猜测。

luna 负责已明确入口、预期行为和检查方式的有界任务，例如核对一个页面的验收与版本对应、运行一组已有定向测试、复查一个失败状态或检查一项修复的反例。每项任务同时给出允许读取或修改的文件、原有负责人、完成条件和回执位置。不能只派一句“全面检查一下”。

| 工作 | 6sol | luna |
| --- | --- | --- |
| 范围与版本汇总 | 负责 | 提供局部证据 |
| 复用用户验收 | 作出汇总结论 | 核对已分配条目 |
| 独立行为补验 | 确定风险与预期 | 执行有界复核 |
| 共享边界或口径问题 | 负责判断与协调 | 上报反例和缺口 |
| 全量门禁与最终报告 | 统一调度并收口 | 避免重复启动 |

先复用原窗口现有负责人和独立复核者。只有尚未认领、能够独立完成的任务才追加分配；默认同时最多新增两项补验，不与已有并发资源冲突。作者测试可作为证据，独立复核须注明执行者并检查遗漏或反例，不能让同一代理重复原测试后称为独立复核。

## 执行顺序

### 接住已有成果

主代理先收齐正在运行任务的状态、拥有文件和预期产物。已开始的必要修复由原负责人结束当前批次；读到旧失败记录时先查是否已有后续通过证据，不能重复修复。

在既有进度文件补上范围清单、验收复用结论和剩余阻断。此阶段不新增全仓审计。首个回执应能说明已收口哪些范围、剩下哪些具体阻断、谁正在处理及下一次需要什么证据。

### 完成必要补验

对用户已验收且相关行为未变化的条目，记录复用依据即可。对实际变化的条目，按风险补最小验证，重点检查请求日期与结果日期、API 与页面状态、数据发布与读取版本、失败与重试，以及相关导出或 Agent 消费者。

数据更新后读取新结果的行为，优先复用已有真实请求回执和隔离测试，不主动发起真实更新或历史重算。使用模拟供应商或合成数据时注明替代边界；缺失与零、空结果与错误、旧日期与目标日期不能混用。此处是按影响选择的检查方向，不是每页都要重跑的固定清单。

新反例落入已授权修复范围时交还对应负责人最小修复，再验受影响连接处；超出当前窗口最新授权的改动只登记具体阻断和待决动作。本 PRD 本身不把“仅验收”扩展成无限修复任务。

### 在稳定版本上收齐检查结果

全量检查由原窗口统一调度，正在运行或已经具备有效证据的检查直接接续。复用现有 lint、typecheck、债务审计、前端测试及适用的后端发布门禁，不创建新的门禁体系，不修改基线换取通过。

正式金融修改和发布范围继续遵循 [验收要求](acceptance_tests.md)与最近的路径规则。后端 canonical gate 复用 `scripts/backend_release_suite.py`，解释器和依赖版本以执行窗口已核实环境为准；不能仅凭命令名称相同合并不同环境的结果。

记录检查前后相关源码指纹。检查期间受测路径变化时，该结果只能支持仍匹配的部分；待负责人结束修改后重跑受影响检查。原有失败必须有同条件对照证据；失败、跳过、未执行分别记录，跨批重叠测试不累加。

局部测试、全量门禁、业务对账和日常运行分别给结论。一个健康检查成功或构建成功，不能替代页面行为与业务核对。

### 整理交付版本与运行结论

保留各负责人已有差异、修改前副本和相关证据，整理本次纳入及未纳入内容。沿用正在使用的集成方式；没有冲突隔离需要时，不为收口另建工作树。需要隔离时按现有工作树工具和仓库规则处理，不能从旧 HEAD 开始后遗漏用户已经验收的未提交成果。

本地提交按已有授权和明确路径分批进行，不全量暂存，不动他人的暂存内容，不为获得干净目录执行整树重置、清理或覆盖。共享工作区可以保留未纳入的其他任务；交付版本必须能够说明实际包含什么以及如何复现相关验证。

日常入口通过现有只读运行探针、构建身份及合法页面访问核对，通常需同时识别前端构建、后端相关版本和数据结果版本。`5888`、`5890` 等只是文档中的常见入口，须核对实际使用地址，不能由端口猜测已生效。

目前执行窗口明确未部署。本文不新增部署、服务重启、构建切换、真实数据写入、历史补算或外传内部材料的授权；已有明确会话授权继续有效。需要新增交付动作时，先完成可审查的版本、目标入口、命令和回退安排，再提出该具体动作，不能把未部署写成已生效。

## 完成条件与停止规则

每个现有用户入口都有明确归属和结论，用户已验证的成果得到保留；必要补验完成，交付范围内阻断解决，适用门禁具备与当前受测版本相符的证据，才可报告“本轮验收通过”。正式排除面不因这次收口自动获得晋升。

| 层次 | 可声明的条件 |
| --- | --- |
| 文档完成 | PRD 可阅读、范围和分工明确 |
| 验收通过 | 范围完整、必要证据齐全、阻断为零 |
| 具备交付条件 | 验收通过且交付版本可追溯、可复现 |
| 日常入口已生效 | 指定入口的版本及相关行为已实测 |
| 业务对账通过 | 有相应日期、来源、口径和独立核对记录 |

已完成验收但尚未进行获授权的交付时，报告“具备交付条件，待日常入口验收”。仍有必需门禁失败或业务阻断时，报告具体剩余项及已完成范围，不能写全系统通过。证据不足的条目保留 `PENDING`，不能用模糊的“基本完成”覆盖。

一轮稳定版本的必要检查通过后停止扩大检查。新修复导致相关证据失效时，只重做相应范围；没有新失败、新变化或已证明风险时，不开启下一轮全仓审计。非阻断事项留在现有进度文件的后续项，不自动转为本轮开发。

最终回执先用一段话说明当前能交付到什么程度，再给范围清单、版本、证据链接和剩余动作。以完成的用户行为与剩余阻断为进度，不以提交数、测试数或报告篇数代替交付。
