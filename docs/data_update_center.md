# 数据更新中心

入口为“报表与数据”中的“数据中心”（`/platform-config`）。本页安排已有刷新流程并展示执行记录，不定义新的财务指标。本文中的日期验收记录是相应本机环境的历史证据，不能证明隔离交付树已安装计划任务、加载服务或执行真实重算。

## 使用

在“安排财务更新”选择更新范围和明确的报告日期。“每日余额、持仓与风险”只等待余额来源，适合日常更新；“完整财务更新（包含损益）”还需要相应报告日的损益文件。必需文件到齐后可点击“立即更新”；也可提前选择“资料齐全后自动更新”，随后把文件放入页面显示的投放目录。后台每五分钟检查一次，关闭浏览器后继续执行。该方式需要本机开机、任务所属用户保持登录，并且数据目录及既有数据源可访问。

文件检查复用现有来源命名规则与归档清单，识别债券余额、同业余额和固收损益文件。直接投放的文件必须有明确年份与日期，月度 FI 损益文件沿用月末日期规则；无日期名称不会被自动视作当天文件。文件至少稳定一分钟。汇率沿用已配置来源，非标损益仍执行现有解析规则。

“文件到齐”只代表可以进入正式校验。每日更新执行既有余额与分析流程，核验债券余额、同业余额、债券分析及风险张量的指定报告日结果。完整更新还会在写入前解析该报告日的固收损益文件，并执行正式损益、产品损益、余额变动和来源摘要等既有步骤。所选流程及结果日期核验全部成功后，记录才显示“更新已核验”。失败可能发生在部分步骤已完成之后，本功能不承诺整条链路具有跨步骤事务回滚。

等待中的请求可以取消。普通失败后点击“重新提交此日期”会选中原报告日和范围，检查资料后再提交。回执确认财务主体完成、失败发生在发布或发布前来源摘要检查时，页面显示“财务计算已完成，发布待处理”，提供失败回执和已完成步骤，不提供日期重提快捷入口。

完整财务更新在损益发布或系统读取发布阶段失败，且原请求保留完整、有序的完成回执时，可点击“仅恢复发布”。后台创建关联原请求的新回执，继续校验原回执摘要、结果血缘与当前来源版本，只恢复发布，不重跑财务计算；损益结果已提交时复用该结果。来源变更会阻断发布，失败原因写入恢复回执。完成回执缺失、每日余额更新或来源摘要阶段失败不支持此操作，页面说明原因，由运维核对依赖后处理。操作仍要求原工作流的更新权限。

相同报告日、相同范围的活跃请求合并，带同一幂等编号的请求重复发送会返回原记录。发布恢复请求也遵守幂等和活跃请求约束，失败后再次恢复仍关联最初财务请求。只有尚未开始任何更新步骤的网络连接或锁等待超时可自动重试，最多三次、间隔十分钟。当前步骤、已记录步骤或失败回执任一表明执行已开始时，不能证明没有副作用，故停止自动重放并要求人工复核；财务主体已完成的发布失败沿用仅恢复发布机制。

“更新市场数据”只启动已注册的 `MOSS-DailyDataRefresh`。本功能保留原有每日 18:45 调度及各步骤已有行为，不接收任意脚本、文件路径或供应商参数。计划任务返回成功与财务数据日期分别展示，不代表所有数据均已更新到今天。

## 代理代办更新的执行约定

本节是代理执行数据更新的完整约定。实现入口为 `backend/app/services/data_update_service.py` 与 `backend/app/tasks/data_update_center.py`；写入前先说明本次日期、范围与调用入口。

用户投放文件后说“全局更新”，指本次变更同步到系统相关模块。代理应先读取更新状态、实际投放目录和本次变更文件的报告日期，再按日期选择已有更新范围。只变化余额来源时选择 `balance_daily`；涉及损益时选择 `core_financial`，它已包含同日余额与风险，不再重复提交同日每日更新。历史文件被替换时也需纳入判断，不能仅比较最大数据日期。

先使用指定日期的预检，再提交现有请求。相同日期和范围已有活跃请求时查看该请求，不另启循环或底层脚本；已完成记录只有结合源版本才能判断是否需要重提。提交后通过数据中心回执跟踪，不能仅以命令退出码或计划任务成功推断更新完成。没有操作权限时说明现有权限状态，不得冒用身份、修改权限或无声绕过入口；本机运维代办也应在授权范围内复用请求服务和后台任务，说明调用方式并保留数据中心可见记录。

文件预检主要检查名称、日期、非空和稳定时间，并不保证报表内容类型正确。数据中心后台的核心更新和每日余额更新，会在目标余额来源归档、余额快照写入前，按本次实际选源调用既有严格解析器；仅恢复发布不走这项检查，正式物化仍重新解析实际归档。直接调用底层刷新脚本不属于新增检查的覆盖范围。对本次变更仍应在写入前做必要的内容解析检查；已知锁占用和供应商不可达问题也应先确认，避免把等待与重复失败叠加到长流程中。确定性坏文件只阻塞依赖它的日期，保留错误证据并继续不依赖它的已授权日期；不得通过删除记录、复制邻日值或反复重跑成功步骤与全链路绕过。失败后先核对成功步骤和依赖，再按既有能力恢复；符合条件的发布失败使用“仅恢复发布”，普通重提仍会重新执行所选流程，不提供通用逐步骤断点续跑。

本入口按指定报告日执行，不是自动扫描全部变更日期并增量调度的引擎。当前完整刷新调用 `scripts/run_global_data_refresh.py`，其中产品损益刷新会处理来源目录的历史月份，选择一个报告日不代表所有步骤只处理这一天。代理必须说明实际范围，不能承诺“只算新增文件”或固定耗时；确需优化该步骤时作为独立、可验证的最小改动处理，不在日常更新中另造刷新框架。除非用户明确要求或当前依赖存在经核实的缺口，不自行扩展为整月逐日补算。有直接缺口证据时说明必要日期和原因后执行，不为已授权更新反复索取确认。

完成后分别报告执行状态、实际日期覆盖和未通过的业务质量检查，并验证相关读取接口。若临时停止API以释放写入锁，结束前恢复API并检查健康状态。

计划余额巡检复用每日刷新 host 的维护租约、仓库 API 进程验证、排空和恢复流程。即使余额写入成功，API 恢复失败也会生成失败回执，并保留已完成物化状态。这一路径在维护期间暂停 API，不代表页面可以持续读取；持续读取须另行核验有效快照及实际读取版本。

## 本机部署

使用已有环境中的 PowerShell 执行安装脚本，可重复运行：

```powershell
powershell -NoProfile -File scripts/scheduling/install_data_update_queue.ps1
```

它注册 `MOSS-DataUpdateQueue`，通过隐藏窗口每五分钟执行一次 `backend.app.tasks.data_update_center`，一次最多运行六小时，禁止同任务重叠；既有市场任务不变。手动提交后最迟在下一次检查时执行。首次安装没有更新请求时只检查空队列，不补跑历史数据。

查看状态：

```powershell
Get-ScheduledTask -TaskName MOSS-DataUpdateQueue
Get-ScheduledTaskInfo -TaskName MOSS-DataUpdateQueue
```

撤销调度：

```powershell
powershell -NoProfile -File scripts/scheduling/install_data_update_queue.ps1 -Unregister
```

待处理请求和执行步骤写入现有治理目录中的 `data_update_run.jsonl`，进程中断后记录保留。恢复检查先在指针认可的保留代次中核对任务标识、报告日、工作流和封存摘要；找到仍有效的已提交结果时，仅修复请求回执为完成。较新代次被撤销或损坏不阻断另一合法保留代次的回执恢复。无可核验结果时才将遗留运行中请求标记为失败，未提交候选和已撤销目标不能恢复为完成；该流程不重跑财务计算。页面提供站内异常提示和近期三十条请求记录；本版不发送邮件、短信或外部消息。

## 页面与接口契约

| 接口 | 用途 |
|---|---|
| `GET /api/data-updates` | 实际日期、计划任务、近期记录、当前操作权限 |
| `GET /api/data-updates/preflight?report_date=YYYY-MM-DD&workflow=balance_daily` | 按指定报告日和范围检查文件到齐情况 |
| `POST /api/data-updates/core` | 提交该日期的即时或等待文件更新请求 |
| `POST /api/data-updates/runs/{run_id}/cancel` | 取消尚未执行的请求 |
| `POST /api/data-updates/runs/{run_id}/recover-publication` | 按原完成回执恢复发布，必需 `Idempotency-Key`，返回关联原请求的新回执 |
| `POST /api/data-updates/market` | 请求启动已有每日市场更新任务 |
| `POST /api/data-updates/choice-stock-pit/preflight` | 只读预检指定日期历史股票来源，核对来源摘要与计划摘要 |
| `POST /api/data-updates/choice-stock-pit` | 持久化已审阅的历史股票恢复请求，必需 `Idempotency-Key` |

历史股票恢复范围标识为 `choice_stock_pit_history`，请求必须给出明确报告日、本机绝对来源与备份路径、来源及计划 SHA256 摘要。来源、目标与备份必须是不同文件；目标数据库由后端配置确定，接口不接受任意目标。普通五分钟队列跳过此类请求，须由现有受控维护主机选择明确请求编号执行，并在写入前再次核对来源、计划与备份。它不执行财务更新、不触发系统财务发布，也不提供财务重提或仅恢复发布操作。

每日余额更新检查余额与债券分析的既有刷新权限；完整财务提交和取消还检查正式损益、产品损益、余额变动和来源摘要的刷新权限。市场更新检查对应股票、宏观来源、期货、预交易门禁、脚本执行和新闻导入权限。沿用项目原有用户身份与权限边界，不增加或绕过认证机制。匿名只读环境可查看状态和文件检查结果，不能提交更新；需要先通过既有权限机制配置操作人。

公开更新回执通过字段白名单投影，仅暴露日期、范围、状态、步骤时间和必要恢复摘要；请求人、取消人、幂等编号、内部计算结果、原始异常和本机恢复来源路径不进入响应。历史股票预检仍暴露来源及计划摘要、行数与写入范围供审阅，执行使用持久化的完整参数。

API 查询只读 DuckDB；正式写入继续由既有 tasks 执行。页面不计算财务指标，不把空值改成零，不按计划任务退出码推断数据新鲜度。原数据中心的候选诊断指标与 `PAGE-CONTRACT-PENDING` 披露保留。

债券表的 33 条双估值空白均属于未到期的人民币凭证式国债，应计利息和面值非零；同日报表没有完整自然键重复或可匹配的有效估值。既有批准规则允许损益账面余额在估值缺失时使用面值加应计，但没有规定源公允价值、摊余成本统一补面值，也没有为其他指标定义相同兜底。另有 3 条发行资产支持证券应计空白，另一应收／应付利息列两条明确为零、一条也空；这不是应计金额的替代依据。

同业应计空白中，2772 条本金非零，分为资产 75 条、负债 2697 条；462 条本金显式为零，19 条本金也空。同一产品存在应计有值的记录，因此产品类别或本金为零都不能单独解释应计空白。19 条空本金属于存放同业，其中 17 条共用的同日同币种总账键有非零余额，但科目总额无法确定逐笔本金；另两条没有精确总账匹配，也不能据此补零。

所需业务定义已收敛为凭证式国债各指标的估值缺省处理、发行资产支持证券两类利息字段的关系、同业资产和负债的应计报送或另源计提规则，以及 19 条本金的逐笔还原来源，均为 `PENDING`。已有标准化契约列出必需金额，尚未明确按业务类别解释空白的矩阵；现行严格守卫暂时保留，不能将其工程行为认定为最终业务口径。标准化快照允许存储 NULL，但合并、正式投影和部分消费者仍会降零，仅放宽解析器不能完成修复。
