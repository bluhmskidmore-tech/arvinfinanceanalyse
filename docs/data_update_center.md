# 数据更新中心：当前基础链路

页面入口为 `/platform-config`，仅在真实数据模式下显示更新操作区；后端入口为 `/api/data-updates`。本文件描述代码契约，不表示本机计划任务已经安装、日常服务已经更新或真实财务数据已经重算。

## 选择范围与报告日

每次请求必须选择明确的 `YYYY-MM-DD` 报告日。`balance_daily` 更新该日的余额、持仓、债券分析和风险结果；`core_financial` 调用完整财务刷新，包含上述结果及正式损益、产品损益、余额变动和来源摘要。同一报告日需要损益时，选择 `core_financial`，无需再提交一次 `balance_daily`。

完整财务刷新中的产品损益步骤可能读取源目录内发现的其他月份，并重建相应事实及读取模型。当前实现不能承诺全链路增量或固定完成时间。历史日期重跑也必须显式指定目标报告日。

## 提交前检查

先读取实际输入目录及各模块已落地日期，再查看 `GET /api/data-updates/preflight?report_date=YYYY-MM-DD&workflow=balance_daily|core_financial`。余额范围检查债券与同业余额文件；完整范围另检查固收损益文件。预检要求文件名能证明目标日期，等待文件写入稳定至少一分钟；配置了汇率文件时还检查路径存在。

预检 `ready` 只表示所需文件到齐，不证明文件内容、汇率日期或业务口径正确。执行阶段仍由正式解析和指定日期核验把关。文件未到齐时可以提交等待请求，进入 `waiting_inputs`；立即更新只有预检就绪才受理。确定性坏文件应保留错误回执并处理来源，不靠重复执行试错。

## 请求、队列与回执

`POST /api/data-updates/core` 接收 `report_date`、`workflow` 和 `wait_for_inputs`，并要求 `Idempotency-Key` 请求头。同一用户、同一编号且参数相同的重发返回原回执；同一报告日和范围已有活动请求时也复用该请求。相同编号不能改用其他参数。已完成请求的同一编号仍指向原回执；来源确有变化并需再次刷新时，应先核对来源版本和结果，再使用新编号。

新请求要求本机 `MOSS-DataUpdateQueue` 计划任务可用。`scripts/scheduling/install_data_update_queue.ps1` 定义每五分钟检查一次的计划任务，调用 `scripts/scheduling/drain_data_updates.ps1` 启动 `backend.app.tasks.data_update_center`。计划任务须由运维另行安装并启用；检查间隔不是完成时限。若 API 与 worker 使用不同启动入口，应先核对两端治理目录和 DuckDB 配置一致。

队列执行前再次预检，单次只由一个 worker 持有执行锁。中断于 `running` 的旧回执会标为失败并要求人工核查，不能自动续跑。等待、排队或自动重试中的请求可以取消；运行中的请求不能从页面取消。

回执追加到治理目录的 `data_update_run.jsonl`，每个 `run_id` 的最后一条是当前状态。`GET /api/data-updates` 展示最近请求、步骤状态、计划任务状态和实际数据日期。公开响应只按白名单投影，不包含请求人、取消人、幂等编号或步骤内部计算结果。状态包括 `queued`、`waiting_inputs`、`running`、`retrying`、`completed`、`failed`、`cancelled`。只有尚未开始步骤的 `TimeoutError` 或 `ConnectionError` 可自动重试，最多三次、间隔十分钟；已开始的步骤失败后先核对回执及已落地结果。

`completed` 表示任务返回成功且必需结果表通过目标报告日核验，不等于历史日期覆盖完整或业务对账通过。当前日常 `balance_daily` 在系统只读发布开关关闭时，没有独立发布阶段。验收应分别核对请求状态、结果日期、相关读取接口和必要的业务对账。

## 权限与实施边界

概览和预检沿用数据健康读取权限；提交和取消按所选范围核验 `refresh` 权限。无权限或计划任务不可用时，页面禁止提交，接口也会拒绝。演示模式不发起更新。

隔离测试使用临时目录、合成输入和计划任务替身，只能证明被测代码与合成口径。实际安装计划任务、发布页面和后端、执行真实刷新，以及业务对账，应按对应运行环境分别验收。
